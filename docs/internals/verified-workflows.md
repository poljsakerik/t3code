# Verified workflows

Verified workflows are an opt-in orchestration layer on top of ordinary V2 threads. Planners, implementers, and reviewers are selected through normal `ModelSelection`, messages use normal orchestration commands, and reviewers are app-owned subagents with fresh provider sessions.

The durable state is `ThreadWorkflowState` in [`packages/contracts/src/workflow.ts`](../../packages/contracts/src/workflow.ts). It snapshots the resolved profile and agent definitions at creation so a running workflow does not change when authored files are edited. Ordinary threads have no workflow state.

```text
draft → planning → planned → implementing → checking → reviewing → done
                                ↑              │          │
                                └── revising ←─┴──────────┘
                                       │
                                       └── needs_human
```

[`WorkflowConfigService.ts`](../../apps/server/src/workflows/WorkflowConfigService.ts) resolves global profile YAML/JSON first and repository profile YAML/JSON second, overriding by ID. Profiles reference one planner, one implementer, at least one unique reviewer, and at least one sequential shell check. Agent references resolve against both the project's and the server user's home-directory Eve-style `.t3` catalogs. Project matches take precedence over global matches; ambiguous references within the selected scope fail. The Eve package owns explicit-folder discovery and authored source loading through its adapted `ProjectSource` and discovery code. [`AgentDefinitionLoader.ts`](../../apps/server/src/agents/AgentDefinitionLoader.ts) translates that source manifest into T3 harness configuration and native skill restrictions, independently of workflow roles. These definitions, including fixed harness model selections, are snapshotted into `ThreadWorkflowState`; there is no separate agent YAML schema.

Immediate entries in a reviewer's Eve-style `skills/` directory declare its native skill allowlist. Non-empty skill directories are rejected for planner and implementer definitions. Reviewer dispatches persist the names as `workflowSkillAllowlist` on their run and copy it into `ProviderAdapterV2RuntimePolicy`. Codex translates it to per-thread `skills.config` enablement entries, Claude passes the SDK's main-session `skills` filter, and OpenCode appends per-session deny-all and exact allow rules. These controls remove unlisted skills from model-facing discovery and reject attempts to load them; global provider settings are never mutated. Planner, implementer, and revision turns retain provider defaults.

Verified workflows do not execute Eve's model runtime. Catalog discovery only reads metadata; workflow resolution evaluates trusted `agent.ts` configuration and maps static `openai/<model>` or `anthropic/<model>` references to T3's default Codex or Claude provider instance. API model objects and unsupported runtime settings fail closed, as do authored executable capability slots. Dispatch uses the frozen agent selection ahead of client model selections, including planning follow-ups, revisions, and reviewer backing threads. This keeps every turn on the existing provider harness, including subscription-backed Claude Code sessions. Older persisted snapshots without model selections keep their original thread-selection behavior.

Codex validates assigned names against `skills/list`. Claude passes the configured names directly to the SDK's native `skills` context filter without a separate initialization-inventory preflight. Plugin-qualified names must use the provider's canonical form.

An adapter advertises this guarantee with `workflowSkillIsolation: "native"`. Reviewer turns fail closed on adapters without it. Orchestration never natively forks a reviewer from the implementation thread; it creates a clean native thread and supplies the approved plan and check results in the review prompt so already-loaded skills cannot cross the reviewer boundary.

[`WorkflowCoordinator.ts`](../../apps/server/src/workflows/WorkflowCoordinator.ts) is an event-driven reactor. It resumes incomplete workflows at startup and reacts to plan, run, checkpoint, message, and workflow events. It never marks `done` from agent prose. Completion requires persisted passing check evidence, valid structured reviewer responses, unanimous approval, and an unchanged workspace digest while reviews run.

Reviewers run concurrently in plan mode. The `workflow.update` command creates each reviewer backing thread with `makeSubagentChildThread`, `subagent` lineage, and no inherited workflow state, atomically with its execution node and `app_owned` subagent row. The coordinator then starts the fresh reviewer session with the approved plan and check results. Ordinary delegation requires an active parent run; workflow reviewers belong to an implementation run that has already completed. Their strict JSON results are consumed by the workflow coordinator, so generic delegated-result delivery must not wake the implementer with those responses. One `workflow_verification` turn item per revision preserves the check evidence, reviewer verdicts, findings, and child-thread links rendered by clients. Updating a round reuses its deterministic item ID; a repair creates a new revision ID, so previous rounds remain visible.

During `implementing` and `revising`, provider `assistant_message` turn items are normalized to hidden `workflow_candidate_message` items. Their ordinary assistant conversation messages remain in the provider transcript, so follow-up runs and forks retain the real conversational context. A rejected candidate is never published as completed work. When the workflow reaches `done`, the server appends a normal `assistant_message` turn item for the final candidate after the approved `workflow_verification` item. Clients render that persisted sequence directly; they do not reorder timeline rows, so existing history cursors remain stable when approval appends the completion item.

Any rejection or invalid reviewer result starts a new implementer revision, after which every check and every reviewer runs again. The coordinator dispatches that provider input as a distinct hidden `workflow_instruction` turn item: adapters still receive ordinary turn-start input, but the durable timeline does not model it as a `user_message`. Repeated identical failures and exhausted revision limits transition to `needs_human`; a human-authored message starts a fresh revision with that guidance.

The web command palette currently starts the `default` profile. Workflow metadata travels through the shared launch contract, so other clients can create the same thread kind without provider-specific behavior.
